# 平台物模型定义 v4.1

> 在《物模型定义 v4.0》基础上调整架构：**访问模式定义在能力项层面**
> JSON 写法沿用 v4.0：扁平 key-value + 行内注释，不做类型包装。
> 修订日期：2026-11-04

# 平台物模型定义
- 全面实行平台定义设备、平台定义应用和平台定义业务，解决不同厂商之间设备兼容性问题，设备在不同APP之间兼容性问题，解决业务一致性问题。
- 同时通过物模型自定义项，实现不同厂商设备差异性问题，不同应用开发者业务差异性问题。
- 实现一套既有规则，又开放包容的物模型定义方案。

## 0. 概念设计 Name Design
- 定义规范的命名，保障各方对物模型理解一致。
 - 产品类目： --iottype--平台定义的产品类目，包括：WIFI摄像机、 4G摄像机、 低功耗摄像机、 NVR、 WIFI视频门锁、 定位器等；是平台基于物联网产品系列定义的常用产品类目，产品类目默认设置了一些产品模块配置项，方便客户创建产品时默认带入，产品类目是产品模块的预设配置集合，为方便创建产品的产物。客户可以自定义类目。

 - 能力模块： --module-- 平台根据业务集合定义能力模块，能力模块定义了能力的组合设置和默认配置，例如：图像采集模块、声音采集模块、声音播放模块、图像显示模块、网络模块、工作模式模块等；能力模块是一个业务的集合，是一个业务的预设配置项，为方便创建产品默认带入。客户可以自定义能力模块。

 - 能力项：--identify-- 能力项是具体表达某项业务能力的配置项，例如：某个镜头的编码参数配置，GPS信号参数配置、时间参数配置等；能力项是能力的最小配置组合，能力项里面项拆解出来不能单独完整表达信息。有的能力项就只有一个配置项，有的能力项有多个配置项。客户可以自定义能力项。能力项分为：属性能力项（描述一个完整的业务属性）、业务能力项（描述一个完整的业务的action）、事件能力项（描述一个完整的事件）；
 -- 属性能力项. XXXProperty，定义一个完整的模块属性，通过一堆的keyvalue，完整的表达一个事物。
 -- 业务能力项. XXXService， 定义一个功能业务操作，通过一堆的keyvalue，完整的表达一个操作。
 -- 事件能力项. XXXEvent，定义一个事件，包括事件中携带的属性参数。

 - 参数项：--key--, --value-- 参数项是最小配置单位，是针对一个参数的配置项，包括参数名称、参数类型、参数说明、参数取值范围、参数默认取值、参数取值单位等；参数项是物模型的最小配置单元，客户可以自定义参数项。标准物模型都是由参数项组成。

## 修订说明

| # | 变更 | 说明 |
|---|---|---|
| 1 | `access_mode` 上移到**能力项**，参数不再声明 | 能力项即权限边界 |
| 2 | **属性按业务域聚合**：一般拆为「只读 + 读写」两个属性能力项，具体数量按实际业务定 | 属性 84 → 47；服务按动作拆分（38 个），另加 11 个事件容器（不含接入示例的香薰/电表） |
| 3 | **服务与事件不设访问模式** | 服务是下发动作、事件是上报结果，语义天然确定 |

**访问模式（仅属性能力项使用）**

| 值 | 含义 | 典型 |
|---|---|---|
| `0` | 只读 | 设备上报，平台/APP 不可改（对应平台字段 `r`） |
| `1` | 读写 | 可下发也可上报（对应平台字段 `rw`） |

> **范围界定**：策略 / 自动化联动不属于物模型，由规则引擎或策略中心单独定义。

## 0. 规则

### 0.1 分层

```
产品类目 iottype → 能力模块 module → 能力项 capability → 参数项 param
```

### 0.2 核心规则

| 编号 | 规则 |
|---|---|
| **R1** | 访问模式定义在**属性**能力项，参数不单独设 |
| **R2** | 属性按业务域聚合，一般拆为 `XxxInfoProperty`（只读）/ `XxxProperty`（读写）；**能力项数量不设硬性上限，按实际业务粒度确定**（如香薰机按喷口分左右两项、电表按计量与预付费分两项） |
| **R3** | 服务与事件不设访问模式；服务结果通过事件或属性回读 |
| **R4** | **一个业务操作 = 一个服务能力项**，各服务独立命名（如 `PTZControlService` / `SnapPictureService`）；**不设 `action` 参数做多动作复用** |
| **R5** | 属性与服务分开，字段相同是正常的：属性＝持久配置（影子同步、可回读、重启保留）；服务＝一次性动作（下发、不落库、不回读）。两者并存时字段保持一致 |

### 0.3 写法约定

- 能力项标题：``**`能力项ID` · 中文名（类型 · 访问模式 · 中文模块 Module）**``
- 业务域标题后注明所属模块，例：`### 1.1 图像采集（图像模块 ImageModule）`；
- JSON 体即该能力项的参数集合，扁平 key-value，注释写在行尾；
- 枚举取值写在注释里，完整枚举表见附录 A；
- 一个服务内含多种子类型时（如屏显内容类型），用 `[type=x]` 标注字段的适用范围。

### 0.4 三个标准范例

**只读属性**

```json
{
    "storage_total": 12800000, // 存储总容量，单位 K
    "storage_used": 12800,     // 存储已使用容量，单位 K
}
```

**读写属性**

```json
{
    "storage_erase_flag": 0,   // 自动擦除覆盖，0 满就停写；1 满就覆盖
    "storage_protect_flag": 0, // 存储保护，0 不限制写入；1 限制格式化与写入
}
```

**服务（单动作）**

```json
{
    "storage_file_system": "ext4", // 格式化文件系统，非必须，不传用系统默认
    "quick_format_flag": 0,        // 快速格式化，0 常规；1 快速
}
```

### 1.17 事件能力项（随业务域归档，不设独立模块）

**组织方式**

- 事件能力项随业务域归档，**一个域可包含一个或多个事件能力项**，粒度按实际业务划分；
- 每个事件能力项**固定 4 个参数**，全平台一致；
- 该能力项下所有事件用 `event_id` 的**枚举值**承载（名称=事件中文名，值=6 位事件 ID）；
- 事件不设访问模式；新增事件只往对应能力项的枚举里加一项。

**统一参数结构**

```json
{
    "event_id": 109300,   // 事件ID，枚举，取值见各域清单
    "event_name": "",     // 事件名称，运行时回填
    "event_time": 0,      // 发生时间，UTC 毫秒戳
    "description": "",    // 事件描述，如"客厅检测到人形"
}
```

#### 1.17.1 事件 ID 编码现状

| 现象 | 说明 |
|---|---|
| 长度 | 全部 6 位：`1xxxxx`（设备事件，57 条）与 `2xxxxx`（算法扩展事件，3 条） |
| 序号段 | `1000xx` 基础、`1025xx~1029xx` 厨房与宠物、`1037xx` 呼叫、`1070xx~1079xx` 岗位、`1080xx~1089xx` 车辆/车位、`1090xx~1098xx` 人与设备状态、`1111xx` 鱼类（原 `1103xx~1109xx` 智能场景段已废弃） |
| 与 v4.0 规则的差异 | v4.0 称「第二位＝模块编号」，但现网第二位为 `0 / 2 / 3 / 7 / 8 / 9 / 10 / 11`，与表对不上。需二选一：更新模块编号表，或不再声称第二位是模块号 |
| 结论 | 本文按语义分组；编码规则待第 5 章确认 |

